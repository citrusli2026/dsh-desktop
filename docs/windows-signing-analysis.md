# 社区 DeepSeek Harness 桌面项目代码签名 / 公证方案分析

> 调研目的：为 dsh-desktop（citrusli2026/dsh-desktop，Electron + electron-builder 26.15.3，当前未签名）选择 Windows 代码签名（及 macOS 公证）方案提供参考。
> 调研方式：全部结论基于主源（`raw.githubusercontent.com` 抓取的仓库文件、`gh api` 内容端点），不使用 README/宣传性措辞推断。访问日期：**2026-08-28**。

## 1. 摘要

社区 11 个相关项目中，**只有 2 个真正对 Windows 安装包做 Authenticode 签名**（dataelement/dsh-desktop、cocode-agency/cocode），其余全部发布未签名 Windows 安装包（或把签名列为"未来的发布 gate"）。**没有任何一个项目使用 Azure Trusted Signing / Artifact Signing 等微软托管云签**，也没有发现 SSL.com eSigner、Sectigo 等商用云签配置；DigiCert 只作为 RFC 3161 时间戳服务器出现在 dataelement 和 cocode 的配置里（`http://timestamp.digicert.com`），不能据此推断证书 CA。两个签名 Windows 的项目都把签名动作**移出了 GitHub 托管 runner**：dataelement 用自托管 macOS ARM64 runner + SafeNet UKey 硬件令牌 + Jsign 7.5（`--storetype ETOKEN`，PIN 走 `DESKTOP_WINDOWS_SIGNING_PIN` secret），cocode 用自建内部 HTTP 签名服务（`WINDOWS_SIGN_MODE=service`，X25519 挑战应答，凭据存系统 keytar，签名服务背后的 PKI 厂商不在仓库内可见）。macOS 侧则是另一番景象：9/11 个项目为 macOS 配置了 Developer ID 签名与公证（或至少 ad-hoc 签名），仅数据要素、vibeinging、liguobao、anywhere-labs、cocode、dsh-tauri-desk 走完整签名+公证；bruc3van、qufei1993、myYangyunfan 用 ad-hoc（`identity: "-"` / `signingIdentity: "-"`），zy/EAC 和 FuqiangCraft 完全不签、README 自认未签名。公证工具（notarytool）与 `hardenedRuntime: true` 是普遍事实标准，尚未发现 altool 残存；凭据形式分三派：App Store Connect API Key（dataelement、liguobao、cocode、anywhere-labs 均支持/使用 `.p8` + `APPLE_API_KEY_ID/ISSUER`）、Apple ID + app-specific password（vibeinging 的 `APPLE_ID/APPLE_APP_SPECIFIC_PASSWORD`、dsh-tauri-desk 文档）、keychain profile（vibeinging、cocode 的 `APPLE_KEYCHAIN_PROFILE` 优先）。发布 runbook 方面，dataelement 提供 `docs/release-runbook.md`（UKey 准备、secret 命名、PIN 处理、发布后验证），dsh-tauri-desk 提供 `docs/MACOS_SIGNING.md`（证书申请、p12 转 base64、secret 表），myYangyunfan 有 `.github/RELEASE_RUNBOOK.md`（ad-hoc 签名校验），其余项目把流程写在 workflow 注释里（cocode 明确写"signing remains outside GitHub Actions"）。关于 SmartScreen 信誉，dataelement 在 README 明确写下"Windows 安全警告可能仍会随着发布者建立下载与安装信誉而逐步下降"，这是唯一公开记录"签了名仍可能报警、需要时间积累信誉"的项目。证书主体（公司 vs 个人）在所有仓库中**均不可见**（证书内容在 secrets/硬件令牌里）。综上：社区的现状是"macOS 公证已成标配，Windows 签名是少数派的重装备"，而对我们最有利的信号是 electron-builder 26.15.3 的 `win.azureSignOptions` 和 `win.signtoolOptions`（自定义 `sign` 适配器）两条路径都已被社区代码验证可用。

## 3. 模式归纳

- **模式 1：传统证书 + 自托管/本机签名装备（硬件令牌派）** — dataelement/dsh-desktop。GH 托管 runner 只出未签名产物，自托管机器 + SafeNet UKey（eToken、PKCS#11）+ Jsign 离线签名；规避了托管 runner 无法持硬件令牌、以及把私钥 pfx 放 GitHub secret 的风险。代价是需要维护一台常开的本机 runner 并插着 UKey。
- **模式 2：自建远程签名服务（服务签派）** — cocode-agency/cocode。electron-builder `win.signtoolOptions → sign 适配器` 指向内部 HTTP 签名服务，客户端做 X25519 挑战应答，凭据存系统 keytar；证书/CA 全部隐藏在服务端，仓库里只留合约。签名完全脱离 CI。
- **模式 3：传统 pfx/p12 秘密 + GitHub 运行器（秘密派）** — vibeinging（Windows 有 `WIN_CSC_LINK`、macOS `CSC_LINK` + notarytool）、liguobao（macOS `MAC_CSC_LINK` + electron-builder 内建 notarize）、anywhere-labs（macOS `MAC_CERT_P12_BASE64`、手工机）、dsh-tauri-desk（Tauri `APPLE_CERTIFICATE`）。把 base64 证书放 secrets，在 runner 上签名/公证；证书被浏览器/系统信任即可，但私钥以 secret 形式驻留 GH，key lease 到期需手工轮换。
- **模式 4：不签 / 只 ad-hoc（放弃派）** — bruc3van（ad-hoc + 明示放弃）、zouyuxuan122/EAC、qufei1993（ad-hoc + SKILL 禁止加签名 secret）、FuqiangCraft、myYangyunfan（ad-hoc + runbook）。共享认知：macOS 用 ad-hoc 让 Gatekeeper 显示"未签名来源"而**不是**"已损坏"（bruc3van 注释、myYangyunfan runbook 的 Sequoia 教训），并明确会伴随 Unknown publisher / SmartScreen 警告。

**跨模式事实**：11 个仓库中**零发现** Azure Trusted Signing / 微软 Artifact Signing / SSL.com eSigner / Sectigo KMS 配置；DigiCert 仅作为时间戳服务器（`--tsaurl http://timestamp.digicert.com`）出现于 dataelement 与 cocode。也就是说，**云签（Azure Trusted Signing）目前没有任何社区项目用起来**，但 26.15.3 的 `azureSignOptions`/`signtoolOptions` 路径已被 cocode/anywhere-labs 用其兄弟键验证。

## 4. 对我们的启示

1. **最接近我们栈的参考是 dataelement/dsh-desktop**：同样是 electron-builder 26.15.3、electron 43.4.0、NSIS + electron-updater + GitHub Releases、同为中文社区维护。它的 Windows 全链路（未签名出包 → 签名 → 重建 blockmap/latest.yml → publish 必须等签名成功）可直接照搬；macOS 侧其临时 keychain + notarytool(API Key) + stapler + spctl 校验也是完整且可复制的模板。
2. **签名放进 electron-builder 内 vs 外部后置签名，二选一**：外部后置（Jsign）的好处是签名失败不产生坏产物、不依赖 electron-builder 对自签工具的实现；electron-builder 26.15.3 内建/可插拔的关键是 `win.signtoolOptions`（cocode 用它挂 `sign` 适配器走服务；服务端可换成 Azure Trusted Signing 的实现）与 `win.azureSignOptions`（新的微软云签原生键）。若选 Azure Trusted Signing：CI 全部留在 GitHub Actions、无需自托管 runner 与硬件令牌，代价是证书由微软租户托管、自动为 `YourCompany` 主体、SmartScreen 信任仍靠信誉积累（dataelement README 已公开承认"警告仍会随信誉逐步下降"——不要预期签名后零警告）。
3. **macOS 公证按社区事实标准做**：`hardenedRuntime: true` + 公证凭据优先 App Store Connect API Key（`.p8`，数据要素/liguobao/anywhere-labs/cocode 均走这条），工具用 `notarytool`（无 altool）；ticket 用 `stapler staple` 并 `spctl` 复验。若想省 keychain 维护，vibeinging 的 `APPLE_KEYCHAIN_PROFILE` + 自配空 password 也值得参考。
4. **社区对证书主体的共识为零披露**：所有仓库都无法看到公司/个人主体；发布说明普遍只写"expected publisher"。因此 Certificate Subject 的取舍（个人 vs 公司、需否营业执照/EV）只能由我们自己决定，社区参考价值有限；若用 Azure Trusted Signing 则主体固定为租户组织名，属于相对省事的选择。
5. **若暂时不签 Windows**：仿照 vibeinging/qufei1993 的做法——README 与 release notes 明示"未签名/Unknown publisher/SmartScreen"，并在 macOS 侧至少 ad-hoc（bruc3van 的理由正当：未签名 arm64 会被 Gatekeeper 判"已损坏"，ad-hoc 至少保留"Open Anyway"入口）。

## 5. 未能验证项

- **Azure/云签项目为零**已证实（11 仓库 code search + 文件级抓取无 `azureSignOptions`/keyvault/OIDC 配置），但**没有任何社区定价/成本数据**（Azure Trusted Signing 价格、SSL.com eSigner 订阅、DigiCert KeyLocker 价格），所有仓库均未记录费用。
- **证书主体（公司 vs 个人）全部不可见**：均存放于 secrets/硬件令牌/内部服务；dataelement runbook 仅说"核对 expected publisher"而未指名；cocode 的 `WINDOWS_SIGN_CERTIFICATE_SUBJECT` 只是环境变量名（实际取值不在仓库）。vibeinging 可见的只是 identity **hash**（`26C311958B22397631A857D0482CD2F0EA0BF2AA`），不是主体。
- **cocode 签名服务背后的 CA/厂商不可验证**：`windows-sign-service.cjs` 只暴露 HTTP 端点协议（`WINDOWS_SIGN_SERVICE_URL`），签名后端（企业内私有 CA 还是商业 CA）不在公共仓库。
- **anywhere-labs 的 Windows 发布状态**：仓库内只有未签名构建脚本，README 称"签名是独立的 release gate"——未观察到任何已实现或已发布的 Windows 签名产物/脚本，只能写"mechanism not visible in repo"。
- **vibeinging**：虽然存在 `WIN_CSC_LINK` 证据工作流且能 `forceCodeSigning`，但 v0.2.0 官方 release notes 明言 Windows 安装包**未做** Authenticode 签名——"持有证书但未签发"的现状以 release notes 为准，实际主体与 CA 不可见。
- 个别抓取失败/为空：qufei1993 的 `docs/RELEASING.md` 首次 raw 抓取 404（后经 `gh api contents` 成功）；zouyuxuan122/Deepseek-Harness-EAC 的 `README.en.md` raw 抓取超时（改用 gh api 成功）；FuqiangCraft 的 PUBLISHING_GUIDE.md 签名章节缺位（本身即结论）。
