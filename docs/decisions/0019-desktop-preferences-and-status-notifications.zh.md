# 0019：桌面偏好与状态通知

- 日期：2026-08-26
- 状态：已接受
- English：[0019](0019-desktop-preferences-and-status-notifications.md)

## 背景

shell.6 同时解决两个桌面使用问题：用户需要把唤起快捷键改成自己习惯的组合，
以及在窗口收进托盘后知道 Harness 何时完成、失败或需要确认。快捷键、开机启动和
原生通知都属于桌面壳能力，不应写入上游 Harness 的 `settings.yaml`，也不应让
渲染器获得操作系统级权限。

## 决策

1. 在 `dsh-desktop-controls` 插件的 Harness「设置 → 通用」中提供桌面偏好入口：
   自定义全局唤起快捷键、开机启动、启动后隐藏到托盘，以及桌面状态通知开关。
   偏好保存在 Electron `userData` 下的 `shell-preferences.json`，与 Harness
   配置和 CLI 数据保持边界。
2. 快捷键由主进程校验、注册和持久化；录入必须包含修饰键。冲突或平台拒绝时保留
   旧快捷键并返回可理解的失败状态，不能阻断 Harness 启动。默认仍为
   `Ctrl/Cmd + Shift + Space`。
3. 开机启动只在打包的 Windows/macOS 上启用，默认关闭；启动后隐藏只有在开机启动
   开启时才可选。Linux 和开发态显示为不可用，不伪造成功状态。
4. 桌面通知只接收插件从 Harness 官方 `useSessions` 状态派生的会话/后台任务状态，
   在主进程识别运行态边沿，并在窗口未聚焦时使用 Electron 原生通知提示完成、失败
   或待确认。首次状态仅建立基线，避免页面刷新产生假通知；用户可以关闭通知。
5. 插件和主进程不读取屏幕、截图或 DOM 来推断状态，也不上传状态数据。插件仅向已验证
   的 Harness 来源暴露窄桥接，IPC 继续执行来源校验和字段归一化。

## 后果

- 正面：快捷键、启动方式和提醒强度由用户控制，Windows 菜单栏隐藏时仍能在应用内
  找到入口。
- 正面：通知在 Agent 长时间运行、窗口隐藏时仍提供低打扰的完成/失败反馈。
- 正面：与 Harness 配置解耦，Linux 不支持的原生能力会明确呈现，不产生虚假的持久化。
- 负面：开机启动行为依赖操作系统和打包安装态；Linux 本版没有统一可靠的开关。
- 负面：系统通知可能被全局通知设置静音，shell 仍保留托盘和应用内状态作为可见入口。

## 备选方案

- 把偏好写入 Harness `settings.yaml`：会污染上游配置边界，并让 CLI 感知桌面行为——否决。
- 让 Web UI 直接申请通知或注册全局快捷键：违反渲染层权限边界，且页面隐藏后不可靠——否决。
- 通过截图、视觉识别或 DOM 轮询推断任务状态：不属于桌面壳定位，且官方已有视觉能力——否决。
- 默认开机启动和强制通知：改变用户系统行为、增加打扰——否决。
