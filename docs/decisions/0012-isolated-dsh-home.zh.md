# 0012:桌面数据目录默认独立

- 日期:2026-08-15
- 状态:已接受(取代 [0003](0003-shared-dsh-home.zh.md))
- English:[0012](0012-isolated-dsh-home.md)

## 背景

0003 曾让桌面壳与 CLI 共享 `~/.dsh`,使会话、设置、API key 双向延续。
评审意见反转了优先级:桌面用户期望应用是**自包含环境**——独立的设置、
凭据、会话与插件——安装/卸载桌面版绝不影响 CLI 工作流,CLI 与桌面并行
使用也不会再争抢同一份状态文件。

## 决策

当用户未显式设置 `DSH_HOME` 时,壳为 harness 子进程把 `DSH_HOME` 设为
`~/.dsh-desktop`(`src/main/dsh-home.ts`,由 supervisor 使用)。逃生舱就是
上游变量本身:`DSH_HOME=~/.dsh`(或任意路径)即可恢复共享——变成显式
opt-in,而不再是默认行为。

## 后果

- 正面:隔离可预期;卸载应用即删除一个自包含目录;CLI 与桌面可用不同
  账号/模型/插件并行;不再有两份界面互相污染状态;
- 负面:老用户的会话仍留在 `~/.dsh`(不做自动迁移;把 `DSH_HOME` 指向旧
  目录即可继续);首次启动需要重新填 API key;
- 官网与 README 不得再以"默认与 CLI 互通"作为卖点。

## 备选方案

- 保持共享、把隔离做成设置项:保留了评审明确否定的旧默认——否决;
- 首次启动时把 `~/.dsh` 复制/迁移到新目录:未经用户同意复制凭据,且之后
  两份数据各自漂移——否决;
- 使用 `app.getPath('userData')` 子目录:数据藏进各平台不同的 Electron
  目录,高级用户找不到、也无法指给 CLI 用;命名的 `~/.dsh-desktop` 与上游
  心智模型一致——否决。
