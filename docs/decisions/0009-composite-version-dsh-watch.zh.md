# 0009:复合版本号(dsh + 壳)与上游巡检自动化

- 日期:2026-08-14
- 状态:已接受
- English:[0009](0009-composite-version-dsh-watch.md)

## 背景

壳打包的是精确 pin 的上游 `@deepseek-ai/dsh`,两者各自演进:上游按自己的
节奏发 rc,壳在期间修自己的 bug。单一线性版本号(0.1.1、0.1.2)无法表达
一次发布打包的是哪个上游;对上游新版本的检查此前靠人工。约束:
electron-builder 要求合法 semver;electron-updater 按 semver 单调比较——
构建元数据(`+dsh.x`)在比较时被忽略,若用它编码上游版本,仅上游升级的
发布将永远推不到已装机用户。

## 决策

- 应用版本号与 git tag 采用复合式:**`<dsh 版本>.shell.<壳修订号>**,
  如 `0.1.0-rc.6.shell.3`——上游在前(它主导用户可见行为),壳修订号在后
  (Debian 上游版本-包修订风格)。首个连字符之后全部用点分隔,每个
  prerelease 标识符都在该数值比较的位置按数值比较——上游 `rc.10` 会正确
  排在 `rc.9` 之上,这是 electron-updater 依赖的性质。
- `scripts/version.mjs` 是版本号与 manifest pin 的唯一写入方:
  `show` / `check` / `bump shell` / `bump dsh` / `set`;`bump dsh` 会改写
  manifest pin 并把壳修订号归零。
- `dsh-watch` 工作流每日检查 npm registry(cron `42 1 * * *` UTC)。发现
  上游新版时自动 bump、重建闭包锁文件、重新物化闭包、冒烟验证并开 PR;
  验证失败则改为开 issue——最常见原因是新版触发 24 小时
  `minimumReleaseAge` 下限,次日运行即自行解除。

## 后果

- 与旧线性版本线相比排序重置:`0.1.0-rc.6.shell.3` 排在 `0.1.2-pre.0`
  之下。可接受——pre-1.0、无需要保全的装机基数(所有者决策,
  2026-08-14);此后单调递增。
- 每次发布都是一条可复现声明:tag 直接给出打包的上游版本与壳的增量。
- 既有线性标签 `v0.1.0-pre.0` / `v0.1.1-pre.0` 保留为历史,新标签走复合
  方案。

## 备选方案

- 构建元数据(`0.1.2+dsh.0.1.0-rc.6`):semver 比较忽略它,仅上游升级的
  版本会被 updater 视为同版本而跳过——否决。
- 壳在前的复合式(`0.1.2.dsh.0.1.0...`):上游才主导一次发布的实质,应
  居前——否决。
- 纯跟随上游、无壳修订号(重复打 `0.1.0-rc.6`):上游两次发布之间壳自身
  的修复没有版本空间——否决。
