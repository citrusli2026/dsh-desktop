## 1. 结论与范围

1. **垃圾桶是 P0 数据/视图一致性问题。** 文件移动与垃圾桶自己的列表可以成功，但没有同步
   Harness 的会话目录与工作区状态；不能用“重启后正常”作为验收。
2. **飞书是 P1 产品流程未闭环。** 已有二维码创建机器人、凭证保存与 Sidecar 启停能力，
   但它们分散在原生菜单和手填设置页，缺少统一的应用管理入口、明确的关闭语义与可信的连接状态。
3. **飞书消息降噪是 P1 配置缺口。** 底层已有详细度、流式预览和卡片样式能力，壳未暴露，
   导致默认消息较多。完整需求与测试契约见 [消息降噪 / 卡片样式任务卡](message-display-settings.md)。
4. 建议先修复垃圾桶，再以独立小任务补齐现有设置页的降噪选项，随后完成飞书管理闭环，
   最后做安装包回归。不把三类改动合进一个大提交。

范围假设：用户所说“类似二维码局域网连接”指相近的入口、独立管理窗口和启停体验，
**不是改用 LAN 配对协议**。飞书仍走 cc-connect 的长连接与 DSH ACP。
应用管理首期支持保存多份本地应用配置、只连接其中一份；不做多机器人并发、群聊工作区路由
或跨 Dashboard Environment 自动连接。人工创建应用是高级备用入口，不再是默认路径。

## 2. 垃圾桶：证据、原因与待验证项

### 已确认的断点

- [TrashSection](../../../plugins/dsh-desktop-controls/lib/client.js#L1077) 的 `act()` 执行操作后只调用
  本组件的 `refresh()`；后者只设置 `listTrash()` 和 `listTrashSessions()` 两份局部数据。
  没有刷新 Harness 的公开会话服务。
- [垃圾桶 IPC](../../../src/main/index.ts#L1532) 直接调用文件系统工具，操作完成后没有通知
  Harness 会话/工作区服务或广播资源变更。
- [unarchiveSession](../../../src/main/trash-sessions.ts#L51) 直接改写 `storages/workspace.json`。
  本地安装的 `@deepseek-ai/dsh-workspace@0.2.1-alpha.2` 在初始化时缓存 registry 状态，
  提供服务级 `unarchiveSession()`；这两条修改路径没有被连接起来。
- 资源页“还原”无论资源类型都走 `restoreTrash()`，没有使用已经存在的
  `restoreTrashSession()`。两条会话恢复路径的归档处理不一致。
- [现有 packaged 垃圾桶测试](../../../e2e/trash-ui.spec.ts) 验证文件、索引和垃圾桶面板，
  未验证真实会话在左侧列表中的消失/恢复。会话夹具是简单目录，不是带有效事件的内核会话。
  [现有单测](../../../test/trash-sessions.test.ts) 同样只验证磁盘往返与归档标记。

### 隔离诊断结果

运行 [reproduce-trash-refresh.mjs](reproduce-trash-refresh.mjs)，实际加载当前 `TrashSection`
并点击其删除/还原回调，桥接到真实垃圾桶文件操作，所有文件位于新建临时目录。

| 操作完成后 | 磁盘会话目录 | 垃圾桶会话面板数量 | 公开会话刷新调用 |
|---|---|---:|---:|
| 删除入桶 | 不存在 | 0 | 0 |
| 还原 | 存在 | 1 | 0 |

要求两次操作触发会话同步的断言失败，退出码 `1`，这是**修复前预期的诊断红灯**。
它证明组件回调遗漏公开刷新，不等于已用真实 Electron 左侧列表完整复现全部原因。
脚本使用假的 React hooks/公开服务和简单目录；真实会话与多个客户端的回归必须另补。

TR-01 补充：运行 [reproduce-trash-sidebar.mjs](reproduce-trash-sidebar.mjs)，以隔离 `DSH_HOME`
启动真实 Electron/Harness，向本地模拟模型发送一条消息，生成有效持久会话，再从垃圾桶删除
当前打开但空闲的会话。两次均得到磁盘会话 `0`、真实左侧标题行 `1`；5 秒内未消失，退出码 `1`。
真实模型调用 `0`，模拟模型请求 `2`（答复与标题生成）；临时数据与 Electron 实例均清理。

公开契约核对：`ctx.sessions.refresh()` 为客户端目录拉取；`ctx.workspaces.unarchiveSession()` 为
权威归档修改。Host 的 `sessionController` 没有移除/释放 API；`AgentRegistry.get()` 只返回裸 Agent，
能移除其 Session 的 `AgentHandle.dispose()` 仅由创建方持有。API Session 的创建/恢复路径没有向
桌面插件暴露该能力。TR-02 必须补足创建方协调入口，再执行文件移动；不得绕过能力边界修改私有缓存。

### 不能只加一个“刷新列表”就宣告解决

当前安装内核的公开客户端 `ctx.sessions.refresh()` 可以重新拉取 Host 的会话目录，
`ctx.workspaces.unarchiveSession()` 可以走工作区的权威修改路径，应优先复用。
但 Host 查询还合并驻留内存的 Session：**不在运行不代表已经释放**。
因此删除当前打开但空闲的会话后，仅移动目录和拉取列表仍可能返回旧行。
这条路径需用真实 Harness 测试确认，并核对支持的 Host 释放/移除机制；不要越过公开契约
改内部缓存、造第二份会话数据库或把修改 `node_modules` 当作交付。

另外需要覆盖：

- 归档标记修改后被 Host 的旧内存状态写回；这是待复现的并发风险，不是本轮已观测事实。
- 原路径已有新会话时，通用恢复会生成 `session-id (restored)` 目录；目录名与持久化 header
  的会话身份是否一致尚未验证。会话不能直接沿用普通文件“改名恢复”的承诺。
- 删除中的任务启动、子任务活动、ACP 进程仍持有会话时，单靠 WebUI 最后上报的 `running`
  列表可能不够。后端应提供权威拒绝或协调，不强杀运行任务。
- 磁盘操作成功但视图同步失败时，要显示可重试的同步错误，不能误报已完全完成，也不能重复移动文件。
- 用户反馈的“左侧列表”按会话列表诊断；人工复核还需区分工作区列表、归档列表与预设列表。

也不要让安装全局 CLI 成为 Desktop 二维码流程的前提。

## 4. 建议的飞书产品闭环

设置页提供一个“飞书连接”状态卡片与“管理应用”入口，打开类似 LAN 配对窗口的独立管理窗口。
原生菜单、设置入口复用同一个主进程控制器；不各自维护另一份状态。

1. **创建/添加**：默认二维码创建；显示有效期与进度、支持取消/重试。
   “已有应用”进入高级手填。手机成功后仍需等 Desktop 收到并保存凭据，不能提前声称已连接。
2. **保存应用**：录入本地名称、绑定工作区，保存受保护凭证后显示应用卡片。
   “保存”不隐式替换正在连接的另一份应用；重复 App ID 不创建重复记录。
3. **开启连接**：用户点击后启动 Sidecar，经过分层检查，分别反馈飞书通道与 DSH 状态。
   可提供清楚标注的“保存并开启”组合按钮，不能把尚未完成的步骤合成假成功。
4. **管理**：查看/修改名称、工作区、替换 Secret、重连、切换应用、移除本地配置与凭证。
   切换时先停止旧 Sidecar，停止失败不得启动第二个；重启读取同一份持久状态。
5. **关闭连接**：停止当前连接并持久保存关闭，重启应用或退出 Safe Mode 后仍保持关闭。
   “启动 Desktop 时自动连接”是独立、明确标注的选项；Safe Mode 属于暂停，保留原启用意图。
6. **移除**：删除前确认并停止对应连接；只清理本地记录/凭证，不删除 DSH 会话/工作区，
   不暗中删除或撤销飞书开放平台应用。远端应用管理作为独立外链与说明。

消息详细度、预览开关/间隔、卡片样式与进度展示属于应用的连接设置；先在现有设置页交付，
FS-02 的应用记录迁移和 FS-04 的管理窗口必须保留这些字段并复用相同读写契约。
默认采用 `compact`、开启预览、`3000ms`、经典卡片、逐条进度，不把“静默”解释为不回复。

推荐状态表达：

| 状态层 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 应用已保存 | 本地配置、工作区与凭证保存完成 | 飞书权限/发布/通道正常 |
| 服务已启动 | Sidecar 进程初始化完成 | 飞书 WebSocket 已在线 |
| 飞书通道已连接 | 收到可验证的通道连接信号 | DSH 模型凭证与任务执行必然正常 |
| DSH 配置待完善/异常 | 缺模型凭证、ACP 启动失败等可行动提示 | 不因此把机器人凭证误判为无效 |
| 已验证收发 | 用户显式发起的诊断消息/任务完成一次往返，记录验证时间 | 不承诺永久可用 |

飞书组织审批、应用发布和可用范围仍需用户/管理员按平台要求完成；二维码不能绕过这些条件。
未拿到可靠通道信号前只显示“服务已启动，飞书连接待确认”。不要仅匹配任意日志字符串就宣布收发可用。
缺 `DEEPSEEK_API_KEY` 等模型凭证时，指向现有 Models/credentials 服务，不让用户在飞书配置框填模型 key。
健康检查默认只读；发测试消息必须由用户主动触发，不能在保存/打开窗口时自动发送。

  能力时才做“恢复副本”。普通文件可继续编号另存，不把两类数据混同。
- MSG-01～MSG-04 只暴露受控枚举/布尔/数字；不扩展多项目、多平台、模型选择、角色权限、
  bridge/management/webhook 或自由文本 TOML。默认值变化与显示能力以任务卡为准，不改 Secret/启停/Safe Mode 契约。
- FS-02 迁移成功后保持原连接意图与凭证保护级别；不得把 Secret 复制到应用列表、TOML 或诊断输出。
- FS-03 若需改 cc-connect，先在子模块分支测试、提交、推送，再在父仓库更新 gitlink。
  尽量用有定义的结构化事件，不引入未鉴权的 management API。
- FS-04 新窗口只能取得自己的受限连接管理能力；不得为方便而放宽所有 IPC 的 sender guard 或 CSP。
  关闭窗口不等于关闭已保存的连接；创建中关闭则取消临时流程、清理临时凭据。
- [ADR 0033](../../decisions/0033-cc-connect-sidecar.zh.md) 原定“只在设置集成、不增加扩展入口”，
  与已经交付的原生二维码菜单及本计划存在边界变化。用新 ADR 记录演进，不改写历史 ADR。

## 6. 验收清单与测试边界

### 垃圾桶完成标准

- 删除非运行会话后，垃圾桶新增、左侧移除；还原后反向变化。取消归档后左侧立即可见。
- 正常本地操作在完成确认后 2 秒内一致，无需手动刷新/重启；自动化等待最多 5 秒，超时明确失败。
- 当前选中、未选中、归档、置顶、含子任务等情形有回归；移除当前项后选择有效回退，不留幽灵详情页。
- 永久删除与过期清理不会让会话重新出现；再次重启后状态不倒退。
- 路径冲突和任一步失败不覆盖新数据、不遗失唯一可恢复副本；活动任务拒绝来自权威检查。

### 飞书完成标准

- 新用户从设置进入即可扫码创建、保存应用、开启连接，不要求先找到原生菜单或手抄 Secret。
- 已有应用可以回访管理、切换、关闭、移除；关闭跨重启持久，Safe Mode 暂停行为可解释。
- 手机扫码成功、配置保存成功、进程启动成功、通道连通和真实任务成功不会被混为一个“已连接”。
- 扫码过期、权限/发布问题、凭证无效、网络失败、工作区失效和模型 key 缺失各有下一步指引。
- 截图、UI 状态、IPC 回包、日志、测试报告中均不出现真实 Secret；验证发送有显式操作边界。
- 旧配置缺少显示字段时自动使用 compact/3000ms/legacy/legacy；所有新增选项可保存并回显。
  精简/静默不逐条发送思考与工具消息；静默仍保留最终答复、必要错误与权限交互。
- 完整/精简/静默、经典/富卡片及三种进度展示的组合需回归；关闭流式预览不丢最终消息。

自动测试使用临时 `DSH_HOME` / `userData`、假 Secret、假 QR/Sidecar、模拟 ACP；禁止修改
真实用户目录或调用真实开放平台创建/删除应用。人工验收只对已授权的测试应用/会话操作，
缺凭证或组织审批时准确记录外部阻塞，继续执行可完成的自动门禁。
